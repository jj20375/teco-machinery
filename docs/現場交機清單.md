# 現場交機清單

從「辦公室準備好」到「現場驗收完成、交給客戶」的完整順序。每一步只寫要做什麼和怎麼確認，細節與指令在對應的手冊裡：

| 手冊 | 用途 |
|---|---|
| [`正式機首次部署手冊.md`](正式機首次部署手冊.md) | VM 與主機：更新程式、網路、備份、測試環境 |
| [`IOT_現場接通驗證手冊.md`](IOT_現場接通驗證手冊.md) | 接上設備後逐層排查、數據核對、症狀對照 |

> 指令預設在 VM 上執行（Mac 可以 `ssh teco-vm-tailscale` 進去），目錄是 `~/teco/backend/deploy`。

---

## A. 出發前（在辦公室）

- [ ] **正式機是最新版**：照部署手冊「之後更新程式」同步並重建；`mariadb/init/` 裡的新 migration 都手動跑過
  （目前到 `016`，沒跑的話功能會缺欄位）。
- [ ] **密碼都換掉**：`platform_admin`、`merchant_admin` 的密碼換成新的，存進密碼管理工具；`.env` 的內容也備份到密碼管理工具
  （`DB_ROOT_PASSWORD`、`DB_APP_PASSWORD` 遺失就連不上資料庫；`JWT_SIGNING_KEY` 遺失只是所有人要重新登入）。
  曾經出現在對話或截圖裡的密碼一律視為已外洩，要重換。
- [ ] **準備現場資料**：三個設備的實際 IP（漢鐘 Gateway、DDC1、DDC2）、現場區網網段、東元窗口。
- [ ] **手動備份一次**：`./host-setup/06-vm-db-backup.sh`，確認 `~/backup/` 有新檔案。

## B. 清掉測試環境與測試資料（接設備之前做）

**順序很重要：先清、再接設備。** 清理會停掉 Collector，接設備前清乾淨，第一筆進資料庫的就是真實資料。

### B.1 移除測試環境（附錄 F）

- [ ] VM：`cd ~/teco-iot-simulator && vm/test-env.sh down`（刪掉測試環境的容器、資料庫、映像檔）
- [ ] Windows（系統管理員 PowerShell）：移除 8090、8091 的 NAT 轉送與防火牆規則「Teco Test 8090/8091」，指令在部署手冊附錄 F 最後
- [ ] VM：刪掉 `~/teco-iot-simulator` 資料夾（裡面有測試用的密碼檔）
- [ ] 確認：`docker ps`、`docker volume ls` 都不再出現 `teco-iot-test`

### B.2 清掉正式資料庫裡的測試資料

```bash
./go-live-cleanup.sh
```

先看預覽（**不會改任何東西**）：會列出每張表的筆數與時間範圍、保留的帳號、告警門檻、設備對照。檢查幾件事：

- 讀值筆數如果不是 0，確認它們是測試資料。腳本偵測到「最近 15 分鐘還有新讀值」會特別警告，那代表 Collector 正在寫入，
  可能是真實資料，清掉就回不來。
- 帳號清單裡有沒有測試帳號要刪（例如 `qa_admin`、`oplog_*`、`tony_*`、`test_viewer`）。
- 告警門檻是不是客戶要的值。**測試時留下的門檻（例如冰水主機回水 0.6～0.8°C）一接上真實設備就會亮異常**，現場要改。

確認後執行（會先備份、再要你輸入「清除 teco-iot-area」才動手）：

```bash
./go-live-cleanup.sh --apply --delete-user <測試帳號1> --delete-user <測試帳號2>
```

- 清掉：設備讀值、每小時聚合、告警紀錄、連線紀錄、保養履歷與基準點、登入 token、操作紀錄（要保留操作紀錄加 `--keep-operation-log`）。
- 保留：帳號、角色、場館、設備主檔、FCU 樓層配置、設備自訂代碼、告警門檻。
- 備份在 `~/backup/pre-go-live_*.sql.gz`，不會被每日備份的清舊檔機制刪掉。
- 場館擁有者與平台帳號不能用這支腳本刪。
- 清完 **Collector 是停著的**（到現場要先改 IP），所有人要重新登入。

## C. 到現場：網路與設備

- [ ] **VM 連得到設備**（接設備前最重要的一步）：在 VM 上對三個位址測 TCP 連線（漢鐘 4196、DDC1／DDC2 502），
  方法見驗證手冊「第 1 層：網路」。**目前 VM 是掛在 NAT 後面，能不能連到現場設備網段沒有實測過**，連不到的話看部署手冊附錄 B（改 External 交換器並固定 IP）。
- [ ] **區網看得到網站**：確認 Windows 防火牆 8081 規則的來源網段包含現場網段（附錄 E）；現場網段跟辦公室不同的話要改。
- [ ] **遠端連線仍然可用**：Tailscale、AnyDesk 在現場網路下能連（附錄 A）。

## D. 填 IP、啟動 Collector

- [ ] 編輯 `.env`（只改這六個）：

```
HANBELL_IP=<實際位址>    HANBELL_PORT=4196
DDC1_IP=<實際位址>       DDC1_PORT=502
DDC2_IP=<實際位址>       DDC2_PORT=502
```

- [ ] 啟動（**不能用 `restart`**，它不會重讀 `.env`）：

```bash
docker compose up -d collector
```

## E. 驗收 IoT 資料有接上

用平台帳號登入，身分選「平台管理」→ **系統診斷**（`/platform/diagnostics`）。細節與排查見驗證手冊第 2、3 節。

- [ ] 三條通道（漢鐘、DDC1、DDC2）都「已連線」、讀取成功，約 1 分鐘內有資料進來
- [ ] **FCU 台數**：DDC1 收到 64 台、DDC2 收到 31 台，「收到但沒對照」「有對照但沒收到」兩個清單都是空的
- [ ] **冰水主機數值**逐欄跟現場面板或東元人員的讀數核對（驗證手冊第 4 節）：出水／回水溫度、電流、電壓、高低壓（**單位待確認**）、運轉時數
- [ ] **時間沒有偏移**（診斷頁沒有「時間差」紅燈）
- [ ] **資料有寫進資料庫**、背景排程有在跑（診斷頁的「資料庫落地」「排程」區）
- [ ] 前台戰情室（`http://<主機 IP>:8081`）冰水主機與 FCU 都有真實數值，不是 `--`
- [ ] 平台帳號與場館帳號都能正常登入

> 已知行為：DDC 底下**任何一站故障，整層 FCU 都會顯示離線**（供應商 DLL 的行為，見 `IOT_現場接通驗證手冊.md`）。
> 看到「整層離線、但診斷頁顯示已連線」時，先查 DDC 後面的線路與各站控制器，不是 DDC 本身。

## F. 現場設定（用真實資料設定）

- [ ] **FCU 樓層分區對照**：目前是驗收用的模擬對照，不是真實物理位置。到「空間設備配置」依現場實際位置重新拖拉並**存檔**
  （存檔後做一次移動設備再存的操作，確認真的存得進去）
- [ ] **設備自訂代碼**：FCU、冰水主機依客戶習慣填寫（系統編號與供應商編號不能改）
- [ ] **告警門檻**：冰水主機（出水／回水／溫度差）與 FCU 室溫，照客戶需求設定；存檔後約數秒生效，超標要持續 60 秒才告警
- [ ] **保養間隔**：冰水主機設定間隔；從設定那一刻起算
- [ ] **客戶使用的帳號**：新增場館帳號、指派角色；告知「場館擁有者」不能被刪除或停用，其他管理員只有擁有者能管理

## G. 交機後

- [ ] **24 小時觀察**（驗證手冊第 5 節）：聚合整點持續前進、連線紀錄沒有異常頻繁斷線
- [ ] **備份有在跑**：`~/backup/` 每天新增；Windows 主機的拉取備份排程有執行（附錄 D）
- [ ] **重開機測試**：VM 重開後所有容器自動回來、Collector 自動連上設備
- [ ] **交付**：帳號密碼、`.env` 備份位置、兩份手冊；Tailscale 帳號歸屬要改到客戶或公司名下（附錄 A）

## 現場最常遇到的狀況

| 現象 | 先看 |
|---|---|
| 三條通道都連不上 | 第 C 節：VM 到設備網段的網路；IP 填錯；`.env` 改完用了 `restart` 而不是 `up -d` |
| 連得上但讀取失敗 | 驗證手冊第 3 節症狀對照（DDC 某一站故障、通訊參數） |
| FCU 台數對不上 | 診斷頁的台數比對清單，會列出缺漏與沒對照的 (通道, 站號, 位置) |
| 數值全部是 0 或不合理 | 驗證手冊第 4 節；合理範圍是暫定值，現場拿到真實讀數後要校正（`DataValidationRules.cs`） |
| 一接上就亮一堆異常 | 告警門檻還是測試值，見第 B.2 節 |
| 告警清單出現「DDC1／DDC2／漢鐘 Gateway 離線」 | 該通道連續 60 秒讀不到資料：先看平台「系統診斷」是連線中斷還是某一站故障；接上設備後恢復讀取會自動結案 |
| 改了設定沒反應 | Collector 要用 `docker compose up -d collector` 重建才會重讀 `.env`；告警門檻則是存檔後數秒自動套用 |
